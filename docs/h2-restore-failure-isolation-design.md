# H2 同步恢复失败隔离与自动重新上线方案

日期：2026-11-08。状态：完整 Manager 的隔离双节点灰度已完成，最终制品和结果见第 25 节；升级/回退边界沿用第 24 节。版本仍为 3.7.1-SNAPSHOT，11 月 7 日基线已有本地提交，本轮追加修复未提交、未推送、未部署生产。前文保留设计和分阶段验证记录，以最终结论为准。

## 1. 目标与范围

保留正常的自动同步、自动激活，以及故障消除后自动重新同步并上线。不得将 H2 破坏性恢复后的上线统一改成人工确认。

本次只封住已核实的事故链：清库或导入失败被当成成功，目标被激活/选主，再把空库反向同步。连接为何关闭仍未最终确定，不以修改超时替代安全保护。

非目标：修复历史业务数据、自动选择历史备份、自动回滚、增量追赶、重写仲裁算法、通用任务平台、额外后台线程、跨项目修改。

原则：复用现有同步写锁和自动激活调度；只有现有机制不能成立的地方补保护。没有可信源、旧任务仍未退出或状态无法确认时保持隔离并告警；条件恢复后自动处理，不设置必须人工点击的常规关卡。

## 2. 已核事实

以下是基线提交 7122fab 的源码事实，不含本工作树修复，不是对现场运行状态的推断：

| 位置 | 当前行为及限制 |
| --- | --- |
| `dialect/h2/DbRestore.restore` | 备份、DROP、RUNSCRIPT；异常返回 false，finally 清理输入并解除 syncing |
| `dialect/h2/H2Dialect.restore` | 丢弃新旧恢复命令结果；上传失败可能正常返回 |
| `state/sync/SyncMgrImpl.execute` | null 时最多调用三次；不能用于破坏性恢复重试 |
| `sql/DatabaseClusterImpl.activate(database, strategy)` | 写锁覆盖 synchronize、回调、activate 调用；退出时 finally 解锁，不等待迟到远端操作 |
| `sql/DatabaseClusterImpl.activate(database, manager)` | 先加 balancer/setActive，再传播活动状态 |
| `state/distributed/DistributedStateManager.activated` | 发 ActivationCommand 和 SyncActiveDbsCommand，但不检查所有接收结果 |
| `sql/DatabaseClusterImpl.recoverDatabase/checkActiveDatabases` | 可直接恢复活动库，不能只在同步入口校验隔离 |
| `state/health/ClusterHealthImpl` | 存在历史主、backup、有效 token、空节点和强制回退等候选路径 |
| `lock/distributed/DistributedLock` | masterLock 只协调锁获取；实际写锁通过成员命令持有/释放，没有恢复操作代次 |
| `DistributedLockManager.removed` | 成员离开会清理其远端锁；必须同步失效恢复放行资格 |

锁通道和状态通道分开，不能假设跨通道消息按发送顺序执行。普通 JDBC 事务使用现有 readLock(null)，同步使用 writeLock(null)；直接绕过 HA-JDBC 写物理数据库不在该锁的保证范围，验收/部署期间禁止这种并发写法。

事故证据来源：Core 本地证据目录 `manager-212-9-10-20261106/排查结论.md`。现场版本为 HA-JDBC 3.6.70、H2DB 2.3.3。报告核实恢复 false 被丢弃、空库反向同步；未证明连接关闭的最终原因。本方案不复制数据库脚本或凭据。

## 3. 最小实现组成

只增加 H2 恢复专用保护，不扩成通用工作流：

1. 严格检查结果，恢复请求单次发送。
2. 目标端每数据库一份持久恢复记录；每个参与成员每目标一份激活意向，发起端决定也保存在其中。
3. 一个与现有同步写锁生命周期关联的短期会话凭证。
4. 在既有激活/健康/选主/导出入口使用统一资格检查。

第三项不能省略：generation 只能拒绝旧恢复请求，不能证明原同步写锁仍有效。现有锁没有这种凭证，不能把“同一个成员仍在线”或“数据库当前有人持锁”当作替代。

## 4. 两种标识各司其职

### 4.1 持久恢复记录

字段：格式版本、数据库稳定身份、generation、operationEpoch、operationId、输入 SHA-256、状态。失败阶段在 SQL 接入时补充；不得记录密码或 SQL 内容。

| 状态 | 含义 | 能否参与服务/选主/作为源 |
| --- | --- | --- |
| READY | 已完成一致性条件下的激活收口 | 仍须满足原有 HA 条件 |
| APPLYING | 已接受恢复，可能正在备份/清库/导入 | 否 |
| RESTORED | 导入和基础校验完成，尚未确认激活 | 否 |
| FAILED | 执行失败、执行中重启后结果未知、未完成任务的会话失效 | 否 |

generation 由目标端推进，表示接受操作的顺序，不是成功次数。失败不回退。首次基线与数据库身份不可自动重置；溢出、损坏、身份变化均拒绝破坏性操作。

operationEpoch 是已接受恢复所属的同步会话代次，也必须持久化。导入完成事实可在重启后保留为 RESTORED，但不保留内存会话授权。确认 READY 必须同时匹配目标身份、operationEpoch、operationId、输入摘要和实际恢复 generation 的持久 COMMIT，不能把新一轮锁凭证套在旧导入结果上。

记录位于数据库对应的持久服务目录，不在 /tmp，也不存入被 DROP 的库。采用同目录临时文件、可靠落盘和原子替换；部署文件系统的目录持久化保证必须实测。失败时不能执行 DROP。禁止普通备份恢复覆盖该记录；整机快照回退/记录被人为删除不属于普通重启，需要重新核验身份，不能从 generation=0 静默继续。

### 4.2 同步会话凭证（内存）

一次成功取得同步写锁对应一个唯一 sessionId，绑定发起成员 incarnation 和当前参与成员视图。它不是新仲裁 token，也不持久延长锁租约。

凭证必须随本次写锁获取在参与节点建立，全部确认后才能开始导出/恢复。接受凭证必须发生在对应锁获取处理内；禁止通过一个可迟到的独立“注册会话”消息重新打开已释放的会话。

恢复、激活、解锁必须核对同一凭证。接收端在一个短临界区内串行判定“激活”与“会话关闭”；数据库 IO 不放入该临界区。解锁、所有者离开、视图失效、停止和重启使凭证失效。迟到的旧 acquire/release 不能建立或释放另一轮会话。

重启不恢复旧凭证。RESTORED 也不能因磁盘上有成功结果就获得新凭证。

**实施约束：需要恢复专用的锁获取/释放消息或等价接缝。不得无依据修改已有命令 serialVersionUID；不重写普通业务锁。接口原型必须先证明上述顺序，才能继续自动激活实现。**

## 5. 接口和幂等规则

恢复专用命令携带：数据库身份、sessionId、operationId、expectedGeneration、输入摘要和路径。结果携带相同身份、实际 generation、状态和稳定失败阶段；不再把 null 当作成功。只读状态查询不得触发恢复或激活。

目标端每数据库仅一个实际执行者：

1. 验证来源、当前会话以及目标处于可恢复而非正在服务的状态。
2. 同一已接受 operationId，按原请求身份和摘要识别重复：记录的接受代次应等于原 expectedGeneration+1，不能拿原 expectedGeneration 与已推进的当前值直接比较而误拒绝。执行中只返回状态；完成只返回原结果，不重做。旧结果不是新激活授权。
3. 新操作要求 expectedGeneration 精确等于当前值，且旧执行者已经退出；持久写入 generation+1、APPLYING 等完整记录后才允许清库。
4. 同 ID 不同输入、旧 generation、未来 generation 全部拒绝。
5. generation 和记录更新采用同一串行保护，不允许“先检查，再由另一线程推进，最后仍执行旧请求”。
6. 执行完成写回时再次匹配数据库身份、generation、operationId 和输入摘要。迟到完成不得覆盖另一轮记录；会话已失效时只能记录执行结果并保持隔离，不能写 READY。重复请求的状态答复也不能重新取得已失效的会话资格。

恢复请求只有一次实际发送；状态查询可以重试。新旧恢复命令回退不再用于受保护的破坏性恢复：旧节点不支持此能力时明确拒绝，不静默降级。保留旧类并不代表允许绕开保护执行。

同一操作超时后，不换 ID 重发。不同 ID 的新一轮只能在旧任务退出、旧会话已失效、重新取得写锁并重新导出可信源之后创建。

单条最新记录足以拒绝更早 generation；查不到的旧操作返回 STALE/UNKNOWN，不能编造历史成功。sessionId 失效同时封住“尚未接受、generation 仍相等”的迟到请求，因此不再另设一个通用取消服务。

## 6. 正常自动同步与上线

1. 现有 AutoActivationTask 选择可信源和待修复目标，读取资格/状态。
2. 取得恢复专用同步写保护，全部参与者持久准备本轮会话；核对两个通道的视图及精确成员集合稳定。
3. 源端在锁内检查用户表、导出。准备时输入摘要为空，导出后在所有参与者只绑定一次真实摘要；上传成功且摘要一致。
4. 目标只有在准备和摘要绑定均确认后才接受单次恢复请求；不能为取得摘要先在无锁状态导出。
5. 目标接受请求、持久隔离；备份成功后 DROP、RUNSCRIPT，独立 JDBC 连接检查用户表，写 RESTORED。
6. 发起端收到明确匹配的成功结果；在同一会话内先持久记录含实际恢复代次的 COMMIT，再传播激活决定，不使用无代次旧广播绕过。
7. 每个成员先持久接受决定、应用本地路由/隔离状态、持久标记本地完成，再释放自己的写保护。保留最新决定供幂等与重启核对，不在正常解锁时删除它；完整收口后才发布同步完成。

“完成”日志应覆盖真实成功边界；导入完成可单独记录，但不得提前宣传整个同步和激活完成。回调失败同样进入失败处理，不吞掉继续成功。

### 激活收口的必要边界

现有 `activated()` 丢弃响应，必须改为可判断结果的恢复专用路径。操作身份校验、隔离解除、活动路由更新不能分成无保护的检查与写入。

- COMMIT 前所有参与成员必须保持写保护；没有目标恢复成功的匹配证据不得产生 COMMIT。
- 每个成员不得先释放自己的写保护，再靠迟到消息补齐自己的路由；尚未应用决定的成员持续隔离。
- COMMIT 已持久化后，完成本地应用的成员可以按原 HA 条件继续；其他成员尚未应答不等于决定未知。安全依赖于它们仍持有写保护，不能在请求超时或发起者离开时擅自解锁。
- COMMIT 前视图改变/所有者离开，使旧会话不再授权新的破坏性操作或激活。COMMIT 后不得反转成 ABORT，也不能以新清库代替决定重放；对未应用成员自动收口，不错误隔离健康源库。
- 本轮状态不得被普通 ActivationCommand、SyncActiveDbsCommand 或旧活动库列表提前提升。

这是需要补齐的局部激活屏障，不是现有代码已提供的保证。必须通过“源在每一个激活确认边界宕机”的测试，证明活动路由、候选资格不会分裂。不能用单目标返回 true 代替该验收。

## 7. 超时后的自动处理

### 7.1 恢复阶段超时，尚未发激活

不再发送恢复；目标继续隔离。关闭本轮会话后可以退出原同步写锁，健康源继续服务。原恢复可能还在执行，但其完成最多产生 RESTORED/FAILED，不得解除隔离或激活。

现有自动激活调度下一轮先处理未决意向：

- 旧执行者仍运行：仅查状态，不清库，不启动第二个执行者。
- 旧执行者已经退出，且有可信源：旧会话失效，新写锁、新 ID、新 generation、新导出，自动重新同步。
- 原写锁已释放：即使旧操作导入成功，也不把旧快照直接激活。
- 无响应或无可信源：保持隔离并告警；后续调度继续检查，不需要固定人工确认。

查询不到操作不代表取消成功；本轮会话必须已关闭或因成员 incarnation/重启失效，旧请求才不会后来被接受。无法证明失效时不能开始会触碰该目标的新操作。

### 7.2 激活阶段超时，可能已有部分成员应用

不能复用上一分支简单解锁返回。继续在写隔离下核对本轮结果：

- 已有匹配持久 COMMIT：只能幂等重放该决定与路由，不得重新 DROP，也不得撤销已经提交的决定。
- 尚无 COMMIT，发起者持久记录 ABORT 后：参与者应用撤销再解除自己的保护，后续自动重新同步。
- 决定无法确认：未应用成员保持必要写隔离并告警。恢复通信后自动核对；不能用超时推断 ABORT，更不能删除记录后恢复写入。

恢复执行的 DROP 不重试；激活确认/撤销必须按操作身份幂等。不得因整体 API 超时强制解锁并遗忘半完成激活。

有成员离开时，使用已有成员视图和仲裁规则决定剩余节点能否继续；本轮未收口目标必须先失效，不能通过降低成员数绕过确认。这可能暂时影响写可用性，但不是人为审批上线；不能同时承诺任意分区下不停写和副本安全。

## 8. 重启、调度和持久意向

- 发起端每目标一份未决意向：操作身份、目标、输入摘要和所处阶段（恢复/激活）；在可能发送对应阶段请求前落盘，确认收口后清理。
- 重启先读目标隔离记录和本机未决意向，再恢复活动库/发布健康信息。不能先 setActive 再检查。
- APPLYING 在重启后按未知失败隔离；旧 JVM 执行者已经不存在仍不代表导入完整，自动重新同步而非继续旧脚本。
- RESTORED 没有有效旧会话，不能自行升级 READY。有匹配持久 COMMIT 则先恢复写保护、重放路由和目标确认；没有提交决定的旧导入不能拿来直接激活，安全撤销后自动新同步。
- READY 只表示上一轮已经完成；启动还要按现有集群恢复规则和未决激活检查，不因单份磁盘记录绕过集群状态。
- 同一目标至多一个恢复/核对工作项。复用现有 cron 任务，在入口合并正在处理的目标；不创建新线程池，不每个 tick 堆积任务。
- 自动失败重试复用现有调度周期，不新增定时器或用户参数；同一次调度不得在异常后立即循环重发。不可达期间只进行有界状态查询，不上传/清库。
- 不允许“旧物理恢复没退出，只因 generation 已变就启动新物理恢复”。互斥保护执行者生命周期，而不只是接收请求的几行代码。

## 9. 统一资格检查与空库保护

同一资格组件供启动活动库恢复、普通/远端激活、健康发布、所有候选筛选、host 落地及实际导出使用。选举响应携带必要的恢复资格/代次；缺失、不支持、不可读不默认为健康。保留原始响应成员集合用于仲裁，只过滤候选，不改变法定条件。

资格检查与受保护动作要有串行边界：导出前仅检查一次后任由并发恢复启动，不成立。现有写锁加目标执行者保护必须保证源检查与导出处于同一有效同步范围。

空库保护：源端 JDBC metadata 至少一张用户表；导出成功；输入与传输摘要一致；目标导入后独立连接至少一张用户表。允许有表无记录，拒绝自动用无表库覆盖另一节点。不按 361 字节、921 张表或 INSERT 行数判定，不自制 SQL 解析器。校验不能证明完整业务数据，真实 H2DB 版本的异常语义必须测试。

## 10. 异常、备份和日志

上传失败、目标错误、文件缺失、false/null 都不能正常返回。记录阶段：校验、备份、清库、导入、校验结果、激活、收口。目标保存原始异常，调用方明确“失败”与“结果未知”，不编造被 RPC 丢失的根因。

旧库备份失败不清库；失败输入和对应备份不在本次 finally 中删除，留作诊断/恢复候选。暂不新增清理线程；成功操作按已有策略清理，未决文件不得被备份轮转清理。保留占用需纳入磁盘告警和验收，不无限反复生成失败备份。

不尝试在已异常连接上回滚 DROP；不自动把旧备份导回生产。关闭异常不得覆盖原始失败；Error 不能变成成功。清理 syncing 仅表示执行结束，不等于解除持久隔离。

## 11. 兼容、迁移与回滚

- JDK8；沿用现有 JGroups 通道，不增加端口、远程服务或认证体系。
- 新增恢复专用消息/结果固定 serialVersionUID；旧命令结构优先不改，不假称旧节点能理解新代次。
- 混合版本禁止这条破坏性自动恢复路径，不回退执行旧 DROP 命令；正常已有业务按原兼容范围运行。
- 存量库首次建立 READY 基线是一次升级迁移：先核验当前库和集群状态，不因文件不存在自动认定健康。新空目标从隔离待恢复开始，由健康源自动初始化。这不是每次同步后人工上线。
- 存在未决恢复/激活时禁止直接降级到忽略记录的旧版。回滚需先完成状态收口；回滚代码不等于回滚数据。
- 真实故障前脚本保全与隔离恢复验证是独立运维工作，本方案不授权覆盖现场。

## 12. 文件范围与实施顺序

## 15. 本会话复审：实施入口与明确停止条件

### 15.1 不能省略的源码约束

再次核对 `DistributedLock.unlock()`：先释放本地锁，再发送成员释放命令。`DistributedLockManager.removed()` 则直接 unlock 已离开成员持有的远端锁。因此，单在 `DatabaseClusterImpl.activate()` 返回前检查 generation，不能封住所有者离开时的窗口。跨通道顺序也不能由发送顺序推导。

拟议的恢复专用路径必须在**每个接收端本地**做到：关闭会话入口 → 使该会话未收口目标不可路由/不可选主 → 释放该会话持有的锁。普通业务锁保持原路径。任一步失败不得用 finally 无条件释放恢复保护后继续报告成功。锁的所有权须显式移交给未决处理者，禁止由已退出调用栈遗忘；不能只删除现有 finally 而留下无人管理的锁。

这里仍有一个必须用代码验证的协议问题：参与者可能在不同时间看到激活结果和成员离开。单机同步块只能保证本地互斥，不能证明所有参与者一致；再增加一次“确认 RPC”也不能自行解决最后一次确认丢失。完整实现不得据此声称已具备原子广播或共识。

## 19. 参与者未决记录与锁释放路径接入（2026-11-07）

新增 H2ActivationIntent，持久保存目标身份、操作代次/ID、源成员 incarnation、输入摘要、精确参与集合和 PENDING/COMMIT/ABORT 决定。本地应用完成单独落盘；COMMIT 和 ABORT 不可相互反转，旧操作不能覆盖新操作。文件缺失、损坏、身份不符或更新失败均不能默认为已完成。初始化目录/存量基线仍未自动启用。

新增 H2RestoreWriteFence，将该记录与已有信号量全局写锁绑定。顺序固定为“决定落盘 → 本地幂等路由应用 → 本地完成落盘 → 解锁”。路由失败时保留同一持久决定及写保护，自动核对可重试路由，但不能重新执行清库。进程重启发现未决决定时恢复写锁；即便磁盘已有本地完成标记，COMMIT 的内存路由也必须在新 JVM 重建一次后才放行。

恢复专用 RestoreLockDescriptor 与普通描述符分离，包含目标、操作代次/ID 和所有者；采用新的 serialVersionUID=1，不修改旧命令的 UID/字段。DistributedLockManager 新增 prepareRestoreLock，MemberAcquireLockCommand 对恢复描述符只核对已有持锁资格，不重新 acquire；MemberReleaseLockCommand 和 removed(Member) 对恢复锁都经过持久状态检查。未收口恢复锁保留，普通锁仍按原规则释放。恢复锁不作为无代次普通锁进入旧状态传输，后续启动/新成员接入必须通过持久意向恢复保护。

管理器每目标只保留最新恢复绑定，完成后的旧描述符不会无限累积；旧 acquire/release 不能操作新绑定。路由回调期间不持有管理器注册表锁，持锁状态使用可见性保证，避免管理器锁与路由回调的监视器反向等待。

已新增并验证：PENDING 重启、COMMIT 决定持久且不可反转、ABORT 拒绝迟到 COMMIT、决定与应用之间保持写保护、路由失败后重试、成员移除与旧释放不解锁、旧释放不能命中新操作，以及 PENDING/COMMIT 下独立 JVM Runtime.halt 后重建写保护。上述独立进程测试只证明进程崩溃边界，不证明物理断电语义。

**当前尚未启用完整生产恢复协议**：普通 H2 同步仍未调用 prepareRestoreLock，新恢复命令的会话/成员视图检查、目标执行者接入、协调者持久决定与自动查询、启动前/新成员发现未决操作、所有激活和选主入口资格检查仍待接入。因此这些锁链测试不是完整自动恢复验收，不能交付生产。目标继续保持为完整生产接入，未提交/推送。

规模审查：DistributedLockManager 新增内容属于同一锁所有权和释放生命周期，尚未拆分其既有状态传输职责；H2 的持久决定及路由屏障分别放入专用组件，不把网络协调或 SQL 执行放入文件记录类。后续若管理器继续增长，应按恢复协议职责提取，不能通过压缩代码绕过规模审查。

## 20. 恢复命令与提交凭据实施进度（2026-11-07）

新增 MembershipSnapshot 和 CommandDispatcher 的可选原子视图入口，旧实现默认不支持，不以缺失 RPC 响应推断成员集合。JGroups 实现从同一 View 读取创建者、视图序号及成员；成员身份使用稳定地址序列化摘要，显示名称变化不改变身份，新进程同名不继承原资格。状态通道和锁通道分别取快照，不能混用成员地址。

新增 H2RecoveryCommand，PROBE/PREPARE/BIND_INPUT/RESTORE/QUERY/APPLY_DECISION 共用显式操作身份，携带两个通道原始视图、各自所有者、目标身份、发起节点稳定数据库 ID 和预期恢复代次。所有新增 wire 类型固定 serialVersionUID=1。命令重反序列化后仍校验必需字段；RESTORE 沿用原 sync allowed-roots 路径边界。无已安装本机 Handler 时返回 UNSUPPORTED，不执行旧清库命令。

激活意向新增发起节点稳定 ID、视图摘要和实际恢复 generation。准备阶段允许空输入摘要，持锁导出后只绑定一次真实摘要；未绑定摘要或没有明确恢复代次时不能 COMMIT。目标日志持久 operationEpoch，旧代次的成功导入不能用于新一轮会话。只有同身份、同操作、同 operationEpoch、同 SHA-256、同实际 generation 的持久 COMMIT 能确认 READY。

重启保留 RESTORED 这一导入事实，但不恢复会话或资格；READY 重启先退为 RESTORED，须在持久 COMMIT 和写保护下重建路由后重新确认。APPLYING 重启仍为 FAILED。以上取代第 18 节早期“所有完成状态一律降 FAILED”的实现描述：区分结果事实与上线授权，才能在提交已经不可逆时重放决定而不是再次清库。

本节阶段的激活意向格式为候选 version=2、恢复日志为候选 version=3；当前候选格式及正式接入状态以第 23 节为准。所有格式均尚未发布/部署，旧候选格式明确拒绝，不静默迁移或清空。

阶段测试：聚焦 39/39；最终 JDK8 `test check jar --offline --no-daemon` 637 tests / 635 passed / 0 failed / 2 skipped，64 秒，jar/verifyBuildMetadata/check 成功。两个跳过仍为既有 XML 用例。初次视图测试暴露 JGroups 3.6 ViewId 不支持 Java Serializable，改为创建者稳定身份+视图序号；另一轮构造阶段读取次数影响测试桩，隔离构造后严格单次快照读取断言通过。未以重试掩盖业务或并发失败。

下一实际接入顺序：

1. 本机参与者处理器：持久目录及存量记录检查；PREPARE/PROBE 在同一目标串行边界读取视图和记录，SQL 在外部执行但开始/结束都核对操作凭据。
2. 启动/新加入成员：状态通道启动后、健康选主和 recoverDatabase 放行前，读取所有当前成员的未决记录；回包必须包含其当前两个通道视图并与本机一致，防止新成员空查询后旧视图准备才落盘。发现未决先建立本地写保护。
3. 协调者：先本地持久准备再远端准备、导出、绑定、单次 RESTORE、先本地持久 COMMIT 再广播；异常时只核对/重放决定，不按超时重发 DROP。提交决定在原参与者获知之前不能被后续操作覆盖，成员重启必须以稳定节点身份对照原进程身份。
4. 统一服务/激活/选主/导出资格检查；保留自动恢复和自动上线，完成实际 H2 及双进程故障验收后才能判断生产接入。

## 21. 外部 H2 服务的物理执行互斥

客户端 JVM 退出不代表外部 H2 TCP 服务端的 RUNSCRIPT 已退出，不能单凭客户端 OS 文件锁释放就启动另一轮清库。恢复连接在备份、DROP、RUNSCRIPT 之前取得 `SET EXCLUSIVE 1`，直到该连接关闭才释放；使用模式 1 保留其他既有连接，不使用模式 2 驱逐连接。不能取得独占时不得 DROP。

当前依赖 H2DB 2.3.1 的真实 TCP 测试已验证：清库后脚本由服务端门闩暂停；强杀独立客户端 JVM，服务端仍由原 Session 持有独占，新连接不能进入；该会话真正关闭后独占释放，可再次连接，实际 INSERT 结果存在。不能只拿脚本末尾门闩当作会话已关闭，也不能只把客户端错误码当作互斥证明。Windows 本机曾观察到拒绝连接表现为 90135 或 90067（recv failed）；测试分别核对原服务端 Session、当前命令和独占所有者，不以泛化的连接失败代替这些断言。另有连续十轮独立客户端强制退出回归。测试只操作本机临时库，不操作现场。H2 官方行为说明：https://h2database.com/html/commands.html#set_exclusive 。Linux 与实际部署制品仍需独立验收。

这不会使 DROP 可回滚，也不授予上线资格。清库与导入仍属一次业务恢复操作，目标必须在连接关闭后通过独立连接检查用户表；失败保持持久隔离。新协议可保留失败输入供有界未决处理，旧公开恢复入口的清理行为先保持兼容；源端在 SCRIPT 前拒绝无用户表的导出，不按压缩文件大小或业务记录行数判断完整性。

恢复连接关闭自动提交并显式 commit，是为了禁止 AUTO_RECONNECT 在原会话失效后悄悄替换独占连接，以及正确提交导入 DML；不是给 DROP 增加回滚能力。真实部分导入测试验证失败可能留下已提交 DDL，未提交 INSERT 则回滚。备份名在时间戳后加 UUID，防止同一秒的下一次空库备份覆盖故障前备份；保留原有最多十份备份规则。

## 22. 持久装载与本机接收器候选（2026-11-07）

新增 H2RecoveryStore，逐目标保存 intent 和 journal，并以 catalog 记录集群、本机、目标身份与首次迁移基线。首次建立与正常打开分开：只允许在服务尚未开放时、经启动方核实基线后显式建立全新目录；正常重启不接受活动库列表重新覆盖旧失败。catalog 或任一已登记文件缺失、损坏、配置身份变化，均拒绝打开。首次建立中途退出留下不完整目录，不自动补齐或重置。记录必须放在数据库之外，不能被 DROP 清除；最终生产路径和自动迁移接入仍待完成，当前没有创建任何运行时生产目录。

Store 在物理任务未结束时拒绝 close，保留 OS 所有权；关闭后资格检查为 false。COMMIT 对本地目标还必须有 journal READY；重启把 READY 降为 RESTORED，保留导入事实但先拒绝服务，待同一持久 COMMIT 下恢复写保护并重新应用本地激活。原有首次活动基线不能覆盖任何后续 PENDING/ABORT/失败。

新增 H2RecoveryParticipant，当前只是经过测试的接收器候选，**尚未向正式 DistributedStateManager 注册**。每目标的 PREPARE/PROBE/QUERY 与开始、完成核对使用同一监视器；SQL 在其外执行，不新增线程或线程池。准备时核对状态/锁双通道视图，取得现有真实写锁并落盘后才应答；重复恢复只查询已有结果，运行中返回 BUSY，失败保持 FAILED，不再发放执行 Ticket。

新恢复命令接收唯一 `.dump.zip` 制品，校验 SHA-256，只允许单个、与本操作文件同名的脚本条目，以 CREATE_NEW 展开；旧解压工具和旧命令不因此扩大权限。源端仍须生成每操作唯一文件名并按单次语义上传。接收器按 INPUT/CONNECT/EXCLUSIVE/BACKUP/DROP/IMPORT/COMMIT/VERIFY 在对应动作前持久记录阶段；阶段记录失败不能继续下一条 SQL。输入损坏、错误条目或不符摘要不得到达 DROP。

发起节点形成 COMMIT 前核对明确 RESTORED 回包的代次、目标、操作范围与双通道视图，先落盘 COMMIT 再传播。接收 APPLY 的成员不直接信任携带的决定，而是在目标监视器外查询当前成员，核对精确回包集合、状态/锁成员一一映射，以及原发起节点稳定数据库 ID 对应的持久决定。决定未知或来源不完整时保持写保护。

成功本地应用顺序仍为“持久决定 → 目标 READY/本地路由 → 本地完成记录 → 解锁”。调用方等待超时不结束物理占用；即使服务端后来完成 SQL，持久 ABORT 也不能被迟到成功反转为 COMMIT。视图变化或 stop 撤销会话后，物理完成只能留下 FAILED；最后一个物理调用退出后再释放 Store 文件锁。PENDING 重启保持写保护并拒绝旧进程恢复会话；已持久 COMMIT 重启只重放路由，不再清库。

本批新增 Store 七项及 Participant 十三项测试，组合真实文件、SemaphoreLockManager 和临时 H2 TCP 文件库；网络决定查询仍由测试桩控制，不冒充真实双节点 RPC 已装配。规模评估：Participant 集中同一恢复接收生命周期，文件记录、写锁所有权、SQL 执行仍各在专用现有组件中；当前不再拆成通用工作流或执行框架。

**仍然阻断生产接入的实际缺口**：源端协调者尚未替换普通 H2 同步；启动装载及新成员未决发现尚未安装；完成决定在全部原参与者获知前的保留/自动查询尚未闭环；所有活动恢复、激活、选主和导出路径尚未统一查询隔离资格；失败输入的有界保留和生产持久目录/迁移、Linux 文件系统与真实双节点故障验证仍未完成。不得将本节接收器测试视为整个产品可生产使用。保留自动恢复/自动上线目标，不改人工确认，不引入临时库切换。

## 23. 正式入口装配候选与真实传输验收（2026-11-07）

第 18–22 节保留分阶段证据，不代表当前仍未接线。本节记录正常 H2 分布式启动、同步和激活链的装配过程；最终验收以第 24 节为准，候选通过不等于已发布或已部署。

### 23.1 当前实现及必要的持久状态

- `DistributedStateManager.start` 在状态通道接收消息前安装 `H2RecoveryRuntime`、本机接收器和旧记录的写保护；通道启动后发现未决，再进入原健康调度。不创建恢复线程或执行器，后续核对复用现有健康轮。
- `DatabaseClusterImpl` 的 H2 dump/restore 入口经 `H2RecoveryCoordinator` 准备、单次执行和持久提交；所有激活、活动库恢复与选主候选检查隔离资格。隔离时删除已有错误路由，不以已有 active 标志绕过。投票/仲裁集合不因资格过滤而缩小，不强制单节点选主。
- 同步明确选择发起节点本地的活动源库，避免 H2 `SCRIPT TO` 在另一台服务器生成文件而本机读取错路径。原公共普通同步构造方式保持；该路径只新增显式源库构造。
- 激活意向候选格式为 **3**：保存实际参与的稳定数据库 ID、两个通道的进程身份和 `allApplied`。只有全部原参与者应用确认后才能持久记录完成证明；已完成参与者随后离开不阻断新操作，未获知决定的原参与者缺失时不得覆盖旧决定。无关但配置中离线的节点不强制在线。
- 恢复日志候选格式为 **4**：保存首份清库前备份的 `pinnedBackup`。失败及后续尝试不覆盖、不按普通十份轮转删除；匹配 COMMIT 成功后才解除保护。它是清库前副本，不冒充已验证可恢复的业务备份。备份清理严格限定同一数据库的命名边界。
- ABORT 在 SQL 尚运行时先持久化并撤销接收会话；物理任务仍占用锁和文件所有权。迟到成功只留下失败事实，不能把 ABORT 改为 COMMIT。成功 COMMIT 应用后关闭该操作会话，才允许下一合法代次。
- 每操作的输入路径由接收端生成并返回，发送端不拼接另一种操作系统的绝对路径；接收端仍核对 `ha-jdbc.sync.allowed-roots`。输入只保留当前及最近十组本目标制品，不删除其他目标或无关文件。

### 23.2 持久目录、迁移和回滚

可选 JVM 参数 `-Dha-jdbc.h2-recovery-dir=<绝对持久目录>`；未设置时使用本地 H2 数据库绝对文件路径加 `.ha-jdbc-recovery`。`~/` 按运行账户的 `user.home` 展开；无法确定绝对路径的部署必须显式设置。分布式内存库不能假装具有跨重启隔离保障。

目录不能位于随部署清空的临时区。集群和本机 ID 的 SHA-256 形成 namespace，外部 `.initialized` 标记先持久化，记录目录为对应 `.store`；单独丢失 store/catalog/任一已登记记录会拒绝启动，不能以旧活动列表重建健康基线。首次迁移只声明没有本协议记录的失败历史，不证明存量业务数据完整；上线前仍需核实原库与备份，不能用迁移掩盖旧版本已经造成的空库。

迁移服务路径或账户时保留数据库及整套恢复目录/标记，不得删目录、改配置指向新空目录来解除隔离。配置的数据库路径/稳定 ID 改变会触发身份不匹配，应按真实迁移处理。未决状态存在时不得降级为不能识别该协议的旧 JAR；停机备份及回退必须覆盖数据和恢复记录，不能只换包。

新命令要求当前成员均支持接收器和双通道原子视图；旧节点在准备前被拒绝。已安装或已停止的旧状态上下文拒绝 legacy H2 恢复命令，不允许迟到旧命令转到新实例。没有修改普通命令的序列化 UID/字段，也没有改变消息协议认证、端口规划或选主规则。

### 23.3 真实传输发现的两项关闭/排队缺陷

最小修复只调整 `DatabaseClusterImpl.recoverDatabase(true)` 的启动等待：统一在过滤旧活动列表、尝试既有允许的本地激活之后，检查真实 balancer 是否已有活动库。没有路由时继续原有有界等待，不把尚未发现或已隔离等同于启动成功；到期明确失败。保持既有 `ha-jdbc.startup.active-database-timeout-millis`（默认 60 秒）和重试间隔，不引入新开关、线程或资格状态，不缩小投票集合，也不解除持久隔离。

状态通道及现有健康调度在等待前已启动，恢复接收器继续处理消息。激活方法本身不锁 `start()` 的监视器，但后续真实重启还暴露 `getLocalDatabase()` 的同步读取会间接等待该监视器。确定性测试已在旧实现复现：主线程持有启动监视器时，其他线程无法读取已识别的本机数据库。最小修复将既有本机 ID 以 volatile 安全发布，识别标记完成后再发布 ID；已识别读取不再取得启动监视器，首次识别仍同步。该读取只返回配置对象，不授予活动、恢复或主节点资格，`start/stop` 同步及所有隔离门禁不变。

正常 `start()` 返回前必须有真实活动路由，避免业务先初始化失败。超过配置截止时间仍未恢复时维持原启动失败及资源清理规则；超长恢复须按既有启动超时配置安排，不承诺无限等待或硬中止底层 SQL。

回归验证发现完成后才交接路由、旧活动列表不能提前交接、持续隔离明确超时、中断可收口；再以完整 Manager 重验首次启动、主备重启及自动同步，不能以 systemd active 或 Finished synchronization 单独判断通过。最终验收结果见下文，暂不新增提交或推送。

首轮修复已恢复双机业务初始化，但完整应用还暴露备节点重复同步：PENDING 期间本机资格暂时撤销时，健康轮无条件清空已确认的远端主机引用；COMMIT 恢复后误走丢主选举，旧有接受远端主机分支又撤销本地激活。最小修复保留该远端引用作为原有拓扑信息，不赋予本机资格；原主机是本机时仍清除。远端离开仍走既有 removed 回调，后续存活/状态检查与选主规则不变。补隔离不能保留本机主身份、远端引用保留及成员离开清除的回归，并以多个自动激活周期内不再重复恢复为验收条件。

最小修复仅对 `DbRestore` 的破坏性执行连接覆盖 URL 参数 `NETWORK_TIMEOUT=0`，等待真实 SQL 返回后由原 try-with-resources 关闭连接。独立验证及普通业务连接继续使用原 URL；保留 RPC 的既有 60 秒超时、语句 queryTimeout、ABORT/generation/激活门禁，不增加线程或放宽隔离。URL 处理须识别反斜杠转义分号，不改写 INIT 等其他参数。H2 JDBC `setNetworkTimeout()` 在该版本为空实现，不能用它冒充已生效。此处无网络读硬截止，物理 SQL 卡住时仍维持隔离，不能将 RPC 超时当作物理完成。补真实 TCP 的成功/失败脚本超过原 URL 读超时测试，要求会话实际释放独占，并重新完成同一最终 JAR 的全量和 Linux 完整 Manager 灰度。

## 26. 现场重启失败的最小追加修复（2026-11-10）

现场只读核查确认：一端在 `restoreWriteFences` 中获取写保护失败、状态通道未能启动；另一端出现锁/状态视图不一致，随后启动路由超时，初始化重试又在 `setLocal(true)` 的 inactive 检查失败。详细脱敏时间线见 `build/reports/manager-212-readonly-20261110/`。这些问题不因 SNAPSHOT 改成正式版本号而消失。

本地已用真实 `SemaphoreLockManager`、持久 PENDING/COMMIT 记录及原接收器复现相同写锁异常：按数据库名重放时，排在前面的 PENDING 会保留全局写锁，后面的已完成记录为重建路由再次申请同一不可重入锁，自行冲突。此复现说明不必有外部抢锁即可出现现场同栈；现场历史锁的精确身份仍不能仅凭已停止的线程反推。

最小实现范围固定如下，不增加协议字段、线程、配置开关或共享锁框架：

1. 启动重放先处理明确终局（COMMIT/ABORT），完成本地应用并释放其写保护；最后处理仍为 PENDING 的记录并保留原全局写排斥。NONE 不参与重放。不跳过 `tryLock`，也不把 PENDING 改判成功。多份互相冲突的 PENDING 或真正被普通业务锁占用时，仍拒绝开放资格。
