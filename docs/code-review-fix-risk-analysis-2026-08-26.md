# HA-JDBC2 现存问题修复风险评审（2026-08-26）

## 1. 背景

本评审承接 `docs/code-review-findings-2026-08-26.md` 中确认的 20 项现存问题，目标是回答另一个维度的问题：**修复这些缺陷时，可能引入哪些新的正确性、可用性、兼容性和运维风险**。

缺陷严重度与修复风险不是同一个概念。P0 表示问题后果严重，不表示可以直接热修；部分 P0 涉及事务边界、锁所有权、破坏性数据库恢复或分布式协议，修复风险本身也很高。相反，部分 P1/P2 的修复边界局部，可以先行落地。

## 2. 目标

- 对 20 项问题逐项给出修复边界、主要回归风险、兼容性影响、回滚难度和验证门槛。
- 区分可直接实施的小修复、必须先评审的行为变更、需要协议/状态机设计的高风险改造。
- 明确问题之间的依赖顺序，避免单项修复相互抵消或制造新的死锁、数据错误和混部风险。
- 给出分阶段灰度、停止条件和回滚原则，为后续实施会话提供约束。

## 3. 非目标

- 本文不修改生产代码，也不替代每个高风险项的详细实现设计。
- 不承诺一次版本解决全部 20 项。
- 不把“增加超时”“改成 `volatile`”“抛出异常”视为天然安全；必须结合未知结果、所有权和调用方行为评估。
- 不执行真实多节点演练、数据库恢复或凭据轮换。

## 4. 评估模型

### 4.1 修复风险等级

| 等级 | 含义 | 实施要求 |
| --- | --- | --- |
| F4 极高 | 改变事务/锁/状态机/远端协议/数据恢复语义，回滚可能无法恢复现场 | 先出专项设计；故障注入；分阶段部署；明确数据恢复手册 |
| F3 高 | 明显改变运行时失败、容量或健康判定行为，可能把隐性错误变成显性不可用 | 功能开关或影子观测；容量测试；清晰停止条件 |
| F2 中 | 修改局部失败路径或构建行为，兼容风险可控但需契约测试 | 小批次合入；最窄回归；可快速代码回滚 |
| F1 低 | 文档、诊断或所有权明确的局部清理，外部行为基本不变 | 常规评审和测试 |

## 5. 核心约束

- 生产代码和修复测试保持 Java 8 源码兼容，除非先完成 CR-P2-03 的版本决策。
- 事务提交、远端 RPC 超时和外部恢复超时都可能产生“结果未知”，不得自动当作失败并重试非幂等操作。
- 数据库激活的安全优先级高于自动恢复速度；同步未明确成功并完成校验时目标必须保持 inactive。
- 分布式命令对象和返回对象可能参与 Java 序列化；新增字段、类型或异常传播必须考虑旧节点。
- 用户提供的 `ExecutorServiceProvider` 不一定由集群拥有，禁止在错误路径中误关闭外部执行器。
- 修复代码可以回滚，不代表被部分同步、删除约束、错误激活或泄露凭据的数据现场可以回滚。

## 6. 逐项修复风险

### 6.1 CR-P0-01 手工事务锁生命周期

**建议修复边界**

在 `LocalTransactionContext` 中引入明确的事务守卫状态：首次手工事务操作时只加一次读锁并创建一次事务 ID，在 `commit`、`rollback`、`setAutoCommit(true)` 或 `close` 的终止路径中只释放一次。

**主要修复风险**

- 正确修复后，用户长事务、忘记提交的事务或卡死 JDBC 调用会长期阻塞数据库激活；这是用可用性换取一致性的必然变化。
- `setAutoCommit(true)` 按 JDBC 语义可能隐式提交，若包装顺序错误，会在实际提交前释放锁。
- DML 抛异常后底层事务是否仍可提交由驱动决定，不能在语句异常时简单释放锁。
- `commit()` 返回异常时结果可能未知；释放锁后允许同步，必须先把未知提交状态纳入 durability/节点隔离策略。
- 同一连接被跨线程使用虽不推荐，但现有 `Semaphore` 锁不具备线程所有权；改成线程绑定锁可能破坏历史用法。

**兼容与回滚**

- 不需要改变远端命令格式，但只升级部分应用实例不能建立全局保证，旧实例仍会提前释放。
- 回滚代码前必须等待所有在途事务结束；带着新语义下的锁直接热回滚可能留下无法配平的计数。

**门禁**

覆盖 commit、rollback、setAutoCommit、close、语句失败、commit 结果未知、重复 end、两线程误用和并发 activate。上线前增加长事务数量、持锁时长和激活等待时长指标。

### 6.2 CR-P0-02 共享读锁一次释放全部读者

**建议修复边界**

普通 `unlock()` 只释放一次 acquisition；另行定义成员离开/集群停止专用的 `drainOwnerLocks(member)` 批量清理能力，不能继续复用普通 `unlock()` 的清空副作用。

**主要修复风险**

- 只把循环改成单次减 1，会使 `DistributedLockManager.removed(member)` 当前“一次 unlock 清空全部”的隐式假设失效，产生僵尸锁。
- 状态传输当前主要序列化锁 descriptor，不完整保存重入计数；严格配平后会暴露恢复计数不一致。
- 立即对重复 unlock 抛 `IllegalMonitorStateException` 可能让停止/成员离开路径中原本被掩盖的不配平操作转成集群停止失败。
- `NodeReadLock` 与底层 `SemaphoreLock` 有两层计数，若只修一层会继续出现过度释放或永不释放。
- `SemaphoreReadWriteLock`/`NodeWriteLock` 也存在一次清空计数的对称实现，需要审计其强制清理语义；但没有测试前不应顺手扩大为全锁体系重写。

**兼容与回滚**

分布式集群必须统一版本部署；混用“普通 unlock 会 drain”与“普通 unlock 只减一”的节点，成员清理结果不可预测。回滚前要确认远端锁表为空。

**门禁**

两读者一写者、同成员多次 acquisition、成员离开批量清理、状态传输后清理、重复 unlock、停止过程中清理。该项必须先于 CR-P0-01。

### 6.3 CR-P0-03 H2 restore 静默成功

**建议修复边界**

先把“上传、命令执行、restore、校验”任一步失败都改为同步失败并禁止激活；本地 H2 破坏性恢复必须单独设计，不应仅删除 `if (!database.isLocal())`。

**主要修复风险**

- 本地 restore 可能对正在打开的 H2 文件执行 `DROP ALL OBJECTS` 或覆盖脚本；`SynchronizationContext` 构造时已经打开目标连接，直接新增恢复调用可能锁冲突或破坏正在使用的文件。
- context 还缓存了恢复前的目标 metadata；restore 后继续用旧连接/旧 metadata 做校验可能得到错误结论，必须用新连接并刷新或绕开旧 cache。
- 必须验证目标确实 inactive、不是源数据库且没有业务连接；ID/IP/local 映射错误会恢复错库。
- restore 失败后目标可能已被清空，代码回滚不能恢复原数据，必须先有备份/临时库。
- 严格检查远端 `Boolean` 会把过去的静默成功变成激活失败，短期可用节点数可能下降，但不能因此继续激活未校验节点。
- 安全路径改造 CR-P1-01 会改变临时 dump 文件位置和远端路径映射，两项必须一起设计。

**兼容与回滚**

若沿用现有命令类型并只严格校验结果，协议风险较小；若新增文件 ID、摘要或命令字段，则必须做能力协商。恢复操作必须以数据备份回滚，不能以代码回滚代替。

**门禁**

本地/远端目标、上传 false、命令 false、命令不存在回退、恢复中断、校验失败、恢复错库保护、进程崩溃后重启。修复完成前建议禁止 H2 dump/restore 自动激活。

### 6.4 CR-P0-04 MySQL 密码泄露

**建议修复边界**

去掉 argv 中的 `--password` 和 `MYSQL_PWD`，改用权限受限的临时 `defaults-extra-file` 或明确支持的平台凭据机制；命令日志统一做参数级脱敏。

**主要修复风险**

- MySQL/MariaDB 客户端版本、Windows 和 Linux 对 defaults 文件路径、字符转义和权限的行为不同。
- 密码包含 `#`、换行、反斜杠、非 ASCII 字符时，错误的配置文件编码/转义会造成认证失败。
- 临时文件崩溃残留仍会泄露凭据；`deleteOnExit` 不足以处理强杀进程。
- 过度脱敏可能隐藏目标、端口和返回码，降低故障诊断能力。

**兼容与回滚**

不建议提供回退到明文 argv 的自动开关。新方式不可用时应 fail closed，并给出明确错误。上线时检查历史日志和诊断包，必要时轮换数据库凭据。

**门禁**

MySQL 与 MariaDB 目标版本、Windows/Linux、特殊字符密码、临时文件权限、异常/强杀清理、日志无密码断言。

### 6.5 CR-P1-01 同步文件默认开放

**建议修复边界**

短期增加显式允许根目录、块大小/offset/总长度上限和启动校验；长期协议使用 `rootId + relativePath` 或服务端文件 ID，不再接受远端绝对路径。

**主要修复风险**

- 直接改为默认拒绝会使所有未设置 `ha-jdbc.sync.allowed-roots` 的现有同步任务失败，包括 H2 临时 dump 路径。
- 各节点目录布局可能不同，相同相对路径需要 rootId 到本地根目录的映射。
- `toRealPath()` 对尚未创建的目标文件不可用；只校验规范化路径又存在符号链接和 TOCTOU 风险。
- 接收端简单拒绝旧发送端的大块请求会造成混部失败或重试风暴，需要上限协商或接收端明确错误。
- 当前不同上传尝试共用 `<path>.tmp`，没有 session/attempt ID；并发同步、重试或迟到块可能互相覆盖。

**兼容与回滚**

建议先发布“配置即校验、未配置告警”的过渡版本，再把默认改为拒绝；保留的兼容开关必须显式标为不安全。协议 v2 需双栈读取或整组升级。

**门禁**

未配置、空配置、多根目录、不同节点根映射、符号链接、父目录替换竞态、路径穿越、超大/负数块、混合版本。

### 6.6 CR-P1-02 差异同步 `versionPattern`

**建议修复边界**

第一阶段优先取消该优化：初始查询直接选择全列，但仍只用版本列判断变化。不要简单在同一 source connection 上增加逐行查询。

**主要修复风险**

- 全列扫描会增加网络流量、LOB 读取和源库压力，大表同步时间可能明显上升。
- 在已有流式 ResultSet 的同一连接上执行第二条查询，MySQL 等驱动可能禁止“多个活动结果集”；逐行查询还会产生 N+1 性能问题。
- 改用第二个源连接可能破坏同一快照，两个连接观察到的数据版本不一致。
- 列顺序、版本列包含在非主键列中的索引映射容易在修复时再次出错。

**兼容与回滚**

不涉及持久格式或远端协议，代码回滚容易；但修复前已经错误同步的目标需要重新全量同步。性能回退需要基准数据决定，不应因理论优化重新引入错误路径。

**门禁**

新增、更新、删除、LOB、复合主键、空表、大表、事务隔离和目标同步耗时对比。

### 6.7 CR-P1-03 按表同步失败非原子

**建议修复边界**

最低限度在 `finally` 尝试恢复约束并保留原始异常；同时引入明确的同步失败隔离状态和人工恢复信息。完整原子性需要按方言评估 staging/影子库方案。

**主要修复风险**

- 半同步数据可能已经违反外键，`finally` 中恢复约束会再次失败；若处理不当会覆盖最初的同步异常。
- `dropConstraints()` 本身可能部分成功后抛异常；若 `restore` 不是幂等操作，必须记录已删除约束清单或定义可重复恢复合同，不能仅靠单一布尔值判断是否补偿。
- 使用 `Throwable.addSuppressed` 可保留双重失败，但运维日志和上层异常转换必须展示 suppressed 信息。
- 多种数据库 DDL 会隐式提交，扩大事务范围并不能回滚 drop/restore constraint。
- 自动重试一个缺约束、半同步的目标可能重复执行 DDL 或放大数据破坏。
- staging/影子库显著增加磁盘、时间和数据库特定切换逻辑，不适合一次性通用实现。

**兼容与回滚**

新增 `SYNC_FAILED/QUARANTINED` 若进入分布式状态，需要协议兼容；短期可仅保持 inactive 并记录本地恢复清单。代码回滚不能恢复已删除的约束。

**门禁**

第 N 张表失败、约束恢复失败、DDL 隐式提交、进程崩溃、重试、人工恢复、不同数据库方言。

### 6.8 CR-P1-04 JDBC 对象 replay 失败被吞

**建议修复边界**

先设计“对象创建/重放失败如何传递到调用入口”。仅在 replay 全成功后缓存对象；失败必须关闭新对象并禁止该节点参与本次调用。

**主要修复风险**

- 只在 `replay()` 中抛异常仍不够：`AbstractProxyFactory.get()` 外层会捕获 `Throwable`，并可能返回已创建的局部对象。
- `ProxyFactory.get(D)` 当前不声明泛型受检异常；为返回 JDBC 对应异常而修改接口可能造成源码/二进制兼容变化。
- 过去被忽略的厂商特定 setter 失败会开始摘除节点，可能从“状态不一致”转成“集群容量快速下降”。
- replay 操作中有些可能是正确性必需，有些可能是 best effort；全部严格失败或全部忽略都不合适。
- 新对象的关闭方式因 Connection/Statement/ResultSet 类型不同，不能假设统一 `Closeable`。

**兼容与回滚**

建议先对 recorded operation 分类，定义 REQUIRED/BEST_EFFORT，再决定异常传播接口。回滚严格策略可能重新接受半初始化对象，不能作为常规容量恢复手段。

**门禁**

每类 setter 重放失败、关闭失败、主节点/备节点失败、全部节点重放失败、异常类型保持、对象不入 map。

### 6.9 CR-P1-05 无活动数据库空结果

**建议修复边界**

在仍可抛出调用入口异常的上层 `InvocationStrategy`/handler 做 balancer 空检查，或调整 collector 接口显式允许抛 `E`；不要用无上下文的运行时异常代替。

**主要修复风险**

- 调用方将从空映射、默认值或后续异常改为立即 SQLException/XAException/IOException，这是正确但可观察的行为变化。
- 修改公开的嵌套 `ResultsCollector` 接口可能影响外部自定义实现。
- 在 collector 与上层都检查时要避免竞态：检查后数据库仍可能被并发摘除。

**兼容与回滚**

若在已有 handler 内完成，二进制风险低；若改接口，应按公共 API 变更处理。回滚容易，但不应恢复空成功语义。

**门禁**

Driver/DataSource/XA/IO 入口、检查后并发摘除、空集群恢复、异常消息和 cause。

### 6.10 CR-P1-06 分布式批量 RPC 失败语义

**建议修复边界**

分两阶段：先停止吞异常并为现有结果补逐成员状态；再引入带 `protocolVersion/requestId/deadline` 的命令信封、幂等处理和未知结果补偿。

**主要修复风险**

- 超时不等于远端失败；远端可能已经成功执行。立即重试 acquire/state mutation 会重复副作用。
- 对所有广播统一“非全成功即失败”可能让一个慢节点拖垮集群；必须区分锁、active set、durability、诊断等命令的失败策略。
- 在不知道是哪一次 acquire 的情况下广播 unlock，可能释放随后重获的锁；补偿必须绑定 requestId。
- 仅有租约而没有 fencing token 时，过期持有者仍可能继续执行受保护操作；新持有者必须能让旧持有者的后续写入失效。
- 租约过期依赖时间语义，不能依赖 CR-P1-10 中不稳定的 Joda 全局时钟，应使用本地单调时间。
- 新命令/返回类型的 Java 序列化在旧节点上可能反序列化失败，正好再次触发本问题。

**兼容与回滚**

需要能力协商、双协议或整组停机升级。新节点写入旧节点不理解的请求身份后，不允许中途回滚为旧协议。回滚前必须 drain 所有新协议在途命令和租约。

**门禁**

三节点部分送达、响应丢失、重复请求、成员离开、网络分区、超时后晚到响应、主节点切换、混合版本、进程重启后的去重。

### 6.11 CR-P1-07 外部 dump/restore 进程死锁

**建议修复边界**

立即并发排空 stdout/stderr、正确关闭 stdin 并使用有界输出缓存；随后再引入可配置进程 deadline 和分阶段终止。

**主要修复风险**

- 输出消费任务本身若使用集群共享执行器，线程耗尽时仍会死锁；应有独立且有界的进程 I/O 所有权。
- 超时过短会杀死正常大库 dump/restore；超时过长又不能满足激活可用性目标。
- `Future.cancel(true)` 或 `Process.destroy()` 不保证数据库客户端及其子进程退出；Java 8 没有完整的跨平台进程树 API。
- restore 被杀死时目标可能已经部分写入，不能仅删除临时文件后重试。
- 输出全部缓存在内存会把管道死锁变成 OOM。
- 命令和输出采集必须与 CR-P0-04 同时做敏感信息脱敏，否则新的诊断缓存会延长凭据暴露。

**兼容与回滚**

输出排空和关闭 stdin 可先落地；deadline 先提供显式配置和指标，再设安全默认。超时现场必须进入 quarantine，代码回滚不能把目标重新激活。

**门禁**

超大输出、无输出、等待 EOF、正常长任务、超时、强杀、子进程残留、输出截断、恢复中断后的目标状态。

### 6.12 CR-P1-08 无界执行器与无界等待

**建议修复边界**

先梳理调用任务图和执行器所有权，再分别设计“编排线程池、数据库调用线程池、健康/同步线程池”。统一 deadline 必须携带到 JDBC query/network 和远端调用。

**主要修复风险**

- 把 cached pool 直接换成小 fixed pool，若任务在池内继续提交子任务并等待，会造成线程池饥饿死锁。
- `CallerRunsPolicy` 可提供背压，但会把阻塞 JDBC 工作带到 JGroups、调度或用户回调线程，破坏线程模型。
- 队列拒绝若映射成普通数据库失败，调用方可能错误摘除健康节点。
- JDBC 取消/中断不保证停止数据库端写入；客户端超时后可能收到“失败”，但数据库稍后提交，自动重试会重复写。
- 用户传入的 `SimpleExecutorServiceProvider` 由外部拥有，集群不能替它关闭或强制更换策略。

**兼容与回滚**

新增容量和 deadline 配置要保留合理默认，并先在 shadow 指标中计算“如果启用会拒绝/超时多少请求”。高负载下从有界池回滚到无界池可能短暂缓解拒绝，但会重新引入资源崩溃风险。

**门禁**

嵌套提交、池满、队列满、慢/挂死 JDBC、写超时后晚提交、取消无效、用户自定义 executor、并发 stop。

### 6.13 CR-P1-09 同步上下文构造失败泄漏

**建议修复边界**

保持现有接口，构造阶段使用局部资源和成功标记；任一步失败时关闭本方法创建的连接并停止本方法创建的 executor，close 异常作为 suppressed/log 保留。

**主要修复风险**

- 必须确认连接由 `database.connect()` 新建且未转移所有权，不能关闭缓存或调用方拥有的连接。
- 清理异常不能覆盖最初的 metadata/connect 异常。
- `shutdownNow()` 在未来构造器增加异步任务后可能中断仍在完成清理的任务；所有权要写入注释和测试。

**兼容与回滚**

外部行为只会从泄漏变成及时清理，兼容风险较低。可作为第一批修复；代码回滚简单。

**门禁**

目标连接失败、源连接失败、getAutoCommit 失败、元数据失败、close 失败、executor 创建后失败。

### 6.14 CR-P1-10 心跳修改 Joda 全局时间

**建议修复边界**

以 `System.currentTimeMillis()` 计算私有 `offsetTime`，`HeartBeatCommand.preSend()` 也必须从系统 wall clock 取时间；`getHostTime()` 返回 wall clock + offset；持续时间和租约使用 `System.nanoTime()`，不再修改 `DateTimeUtils`。

**主要修复风险**

- 宿主应用中若有人无意依赖被修改的 Joda 全局时间，修复后其行为会变化；这是去除副作用但仍需发布说明。
- 新旧节点混部时，对 heartbeat sendTime 的来源和偏移解释可能不同。
- 引入 RTT 平滑、偏差上限会改变选举/可写判定时间，不能和“去掉全局 setter”的局部修复混在一次无基准变更中。
- `offsetTime` 本身也需要可见性保证；只改算法但不改并发仍可读旧值。
- 热部署到同 JVM 时旧代码设置的 Joda 全局 offset 可能继续存在，需要显式恢复 system millis 或进程重启。

**兼容与回滚**

先保持现有秒级取整和接口返回语义，只去除全局副作用；平滑算法单独灰度。建议整进程重启部署，不做类级热替换。

**门禁**

正/负偏差、网络延迟、连续心跳不振荡、混合版本、stop/start、同 JVM 业务 Joda 时间不受影响。

### 6.15 CR-P1-11 健康状态并发

**建议修复边界**

第一阶段用 `volatile/AtomicReference` 修复可见性并增加合法迁移校验；第二阶段把状态事件串行化，但耗时数据库动作和回调不能在持锁或状态事件线程内同步执行。

**主要修复风险**

- `volatile` 不能让“比较旧状态—写新状态—执行 changeState 副作用”成为原子操作，不能宣称问题完全解决。
- 用 `synchronized` 包住 `changeState()` 可能在锁内执行数据库、监听器或远端调用，引入死锁和长阻塞。
- 单线程状态机若直接执行激活/停用，会延迟 heartbeat 和选举；若异步执行，又要用 generation 防止旧动作晚到覆盖新状态。
- 更严格的迁移表可能拒绝当前代码依赖的非规范跳转，造成节点无法恢复。
- 状态更新成功但副作用失败时，需要明确是回滚状态、重试副作用还是进入 degraded。

**兼容与回滚**

若状态只在本地内存中，第一阶段协议风险低；若新增 generation/degraded 并广播，则需要版本协商。回滚状态机代码不能自动逆转已经发生的数据库激活/停用。

**门禁**

并发 HostCommand/down/elect、重复事件、乱序完成、副作用失败、回调重入、调度线程不阻塞、混合版本。

### 6.16 CR-P1-12 `pool/sql` 空实现

**可选方案**

| 方案 | 修复风险 | 兼容性 |
| --- | --- | --- |
| A. 先 fail fast 并标记 deprecated | F2 | 类和方法仍在；原来的 null/隐性失败变成明确 SQLException/UnsupportedOperationException |
| B. 完整实现 JDBC 连接池契约 | F4 | 表面兼容，实际新增资源、事件和并发语义，测试成本最高 |
| C. 直接删除 | F4 | 源码/二进制不兼容，只适合主版本升级 |

**建议**

在没有明确用户需求和契约测试前，先采用 A；下一主版本再决定实现或删除。不要把“从 null 改成能连接”当作小修复。

**实现风险**

完整实现需要定义物理连接与逻辑连接所有权、重复 close、ConnectionEventListener、StatementEventListener、错误事件、并发借还、凭据覆盖和池关闭。任一错误都会造成连接泄漏或把物理连接过早关闭。

**门禁**

先做产品使用调查。若实现，运行 JDBC 契约测试和连接泄漏/事件顺序测试；若下线，提供替代入口和至少一个版本的弃用窗口。

### 6.17 CR-P2-01 TokenStore 静态线程池

**建议修复边界**

明确进程级或 cluster 级所有者。若每集群独立使用，改为实例池；若必须共享，使用引用计数/进程生命周期管理，最后一个使用者退出时再关闭。

**主要修复风险**

- 当前静态池可能被多个 cluster 使用，任一 cluster.stop 直接 shutdown 会中断其他集群健康检查。
- 改成 daemon 只隐藏 JVM 退出问题，进程结束时仍可能丢任务，不是完整修复。
- 改成有界队列后会出现拒绝；拒绝必须映射为明确的健康结果，不能继续返回成功默认值。
- 文件 I/O 可能不响应 interrupt，`shutdownNow()` 不保证线程退出。
- token I/O 超时后任务可能仍在后台完成；调用方若已把默认 token 0 当作真实结果参与选举，会形成不可补偿的错误决定。
- token 文件写入还需要临时文件、fsync/原子替换等提交边界，否则线程池生命周期修复后仍可能读到部分文件。

**兼容与回滚**

不涉及外部 API，但影响多集群同 JVM 生命周期。上线前必须有双集群 stop 测试。回滚前确认新实例池已全部终止，避免新旧池并存。

**门禁**

两个 cluster 共存、先停其中一个、队列满、I/O 不可中断、重复 start/stop、类加载器卸载。

### 6.18 CR-P2-02 可选 observer 未执行

**建议修复边界**

先确认 optional 的业务语义。按当前代码结构推断可能是“必选全部通过，且可选至少一个通过”，但这是提案，不是已确认事实。先影子执行可选 adapter 并记录结果，不影响状态；确认误判率后再启用。

**主要修复风险**

- 直接把循环变量改成 `optionalAdapters` 会让过去被忽略的 ping/connect 结果开始控制节点下线，网络策略或 ICMP 禁用可导致节点批量 offline。
- adapter 异常当前多为 fail open；改成 fail closed 会扩大短暂探测故障。
- `weight` 已排序但当前布尔算法未使用权重，修复循环时不能顺手引入未设计的加权投票。
- CR-P1-11 状态机未修复前，更敏感的探测结果会放大并发状态切换。

**兼容与回滚**

使用 `shadow/enforce` 配置分阶段；回滚到 shadow 不改变 adapter 加载。正式 enforce 必须在 CR-P1-11 至少完成第一阶段后进行。

**门禁**

ICMP 被禁、端口部分开放、adapter 异常、必选失败、可选全失败/单个成功、抖动和状态机并发。

### 6.19 CR-P2-03 JDK/Gradle 构建基线

**必须先做的决策**

区分三个不同目标：

1. 仍用 JDK 8 运行 Gradle 并产出 Java 8 字节码。
2. 允许用 JDK 17 运行 Gradle，但仍产出 Java 8 字节码。
3. 声明产物在 JDK 17 运行时受支持。

目标 2 不自动等于目标 3。

**主要修复风险**

- 升级 Wrapper 可能要求同步升级 `gradle-release` 插件、废弃的 `destinationDir/classifier` DSL、签名和发布配置。
- JDK 17 编译需要显式 JAXB；把 JAXB 依赖直接发布又可能在 JDK 8 形成重复实现或改变下游 POM。
- 继续使用 `javax.xml.bind` 可保持 XML 兼容；贸然迁移到 `jakarta.xml.bind` 会引入包名和配置生态变化。
- JDK 17 运行还涉及旧 JGroups、反射访问、SecurityManager/AccessController 退场和数据库驱动兼容，不应只以 compileJava 成功验收。
- 构建升级可能改变生成 POM、Javadoc、资源过滤、签名产物和发布版本流程。

**建议迁移**

候选过渡线是 Gradle 7.6.x：先确认它在本项目中可由 JDK 8/17 运行并修复旧插件/DSL，保持产物 target 8；再加 JDK 8/17 构建矩阵和显式 JAXB；最后单独做 JDK 17 运行时 smoke。每阶段检查生成 POM/JAR 与上一版本差异。

**回滚**

Wrapper 可代码回滚，但若已发布改变后的 POM/依赖或产物，不能覆盖已有版本，应发新修订版本。发布前必须保留旧 Wrapper 可重现构建记录。

### 6.20 CR-P2-04 GitLab CI 错配

**建议修复边界**

改用仓库 Wrapper 和明确 JDK 镜像，验证任务至少为 `clean test`；publish/release 与普通验证 job 分离，普通 job 不读取发布地址或凭据。

**主要修复风险**

- 切换到 Gradle 会暴露本机用户级 `~/.gradle/gradle.properties` 掩盖的 `snapshotsRepository/releasesRepository` 缺失。
- Linux runner 需要 `gradlew` 可执行位、LF 和可访问的 Wrapper/依赖下载源。
- 缓存整个 Gradle 用户目录可能把凭据、签名材料或污染的动态依赖带入后续 job。
- 现有两个 skipped XML 测试若仍跳过，CI 绿色不等于 XML 配置路径已验证。

**兼容与回滚**

CI 变更本身容易回滚；建议先新增 Gradle 验证 job 与旧 job 并行，确认稳定后删除 Maven job。禁止为了让普通 test 配置成功而注入真实发布凭据。

**门禁**

干净 runner、无用户级 Gradle 属性、无发布凭据、依赖镜像不可用、缓存冷启动、test 报告归档和 skipped 统计。

## 7. 接口与数据结构提案

以下内容是后续专项设计需要冻结的边界，不是本轮已确认实现：

| 领域 | 建议接口/结构 | 关键字段/语义 |
| --- | --- | --- |
| 事务守卫 | `TransactionGuard` 内部状态 | `IDLE/ACTIVE/ENDING/CLOSED`、transactionId、lockHeld；终止幂等 |
| 锁清理 | 普通 `unlock` 与 `drainOwnerLocks` 分离 | owner/member、descriptor、acquisition count；批量清理只能用于成员生命周期 |
| 同步文件 | `SyncFileRefV2` | protocolVersion、rootId、relativePath、offset、blockSize、totalLength、digest、requestId |
| 批量 RPC | `CommandOutcome<T>` | member、requestId、SUCCESS/REMOTE_ERROR/TIMEOUT/SUSPECTED/UNKNOWN、cause 摘要、fencing token |
| 同步状态 | 目标运行态 | INACTIVE、SYNCING、VALIDATING、QUARANTINED、ACTIVE；只有 VALIDATING 成功才能 ACTIVE |
| 外部进程 | `ProcessResult` | exitCode、timedOut、duration、truncatedOutput、terminationMode |
| 健康状态 | 状态事件与 generation | old/new、eventId、generation、触发源；旧 generation 的副作用不得提交 |

## 8. 状态机和时序约束

### 8.1 手工事务

`IDLE -> ACTIVE` 只能加一次锁；`ACTIVE -> ENDING` 后执行 commit/rollback；无论返回成功还是结果未知，都必须记录结果分类，再进入 `IDLE` 或 `QUARANTINED`。禁止“语句结束即回 IDLE”。

### 8.2 数据库同步

`INACTIVE -> SYNCING -> VALIDATING -> ACTIVE` 是唯一成功路径。上传 false、命令 false、进程超时、约束恢复失败或摘要不一致均进入 `QUARANTINED`，禁止自动激活。重新同步必须使用新的 attempt/request ID。

### 8.3 分布式命令

超时后的状态是 `UNKNOWN`，不是 `FAILED`。只有带相同 requestId 的幂等查询/补偿才能解析未知状态；禁止无身份地重复 acquire 或 unlock。

## 9. 异常处理与幂等性

- 原始异常优先；清理/约束恢复/close 异常通过 suppressed 或结构化日志附加，不覆盖根因。
- 对“写是否发生未知”的 JDBC、外部 restore 和 RPC 超时，调用方可见异常必须明确标记 unknown outcome。
- 事务 end、成员锁 drain、同步 attempt、远端 command 都需要唯一身份和重复执行规则。
- 自动重试只适用于已证明幂等或远端确认未执行的操作。
- 任何失败路径都要记录 clusterId、databaseId/member、attempt/requestId、阶段、deadline、结果分类；凭据必须脱敏。

## 10. 兼容性与回滚策略

| 变化类型 | 兼容策略 | 回滚前置条件 |
| --- | --- | --- |
| 本地局部清理 | 同版本直接替换 | 无在途构造/同步任务 |
| 事务/锁语义 | 全部应用实例统一升级 | 在途事务结束、锁表为空 |
| 文件/RPC 协议 | 能力协商、双栈或整组停机升级 | 新协议请求和租约全部 drain |
| 健康状态机 | 先影子观测，再节点级灰度 | 无未完成副作用；数据库实际状态与内存状态核对 |
| 破坏性数据库恢复 | 备份、quarantine、人工恢复清单 | 数据和约束已恢复，不能只回滚代码 |
| 构建/发布元数据 | 比较 JAR/POM/签名产物 | 未发布则回滚 Wrapper；已发布只能发新版本 |
| API 下线 | 弃用窗口和主版本策略 | 下游完成迁移 |

## 11. 灰度与停止条件

### 可影子观测的项目

- observer 新判定只记录不执行。
- 有界池/deadline 先计算“假设启用”的拒绝和超时数量。
- 私有时钟 offset 与旧算法并行计算差异，但不再修改全局时间前需专项测试。
- 严格 replay 先记录 REQUIRED 操作失败率，不立即批量摘除。

### 不适合混部灰度的项目

- CR-P0-02 锁释放语义。
- CR-P1-06 新 requestId/租约协议。
- 新同步文件协议在没有能力协商时。

### 必须停止发布/灰度的条件

- 出现锁计数不能归零、激活等待永久增长或成员离开后残留锁。
- 出现同步失败目标被激活、约束未恢复但未 quarantine。
- timeout 后发现数据库晚提交，而调用方已自动重试。
- 健康状态出现重复 host、乱序副作用或节点批量 offline。
- JDK/Gradle 变更导致 POM、资源或序列化产物非预期变化。

## 13. 分阶段实施计划

### 阶段 0：运行时止血和门禁

- 禁用未修复的 H2 自动 dump/restore 激活。
- 显式配置同步 allowed roots 和块大小上限。
- 关闭可能泄露密码的 DEBUG 日志并检查/轮换凭据。
- 修正 GitLab CI，确保后续改动在干净 JDK 8 环境运行真实测试。

### 阶段 1：局部低耦合修复

- CR-P0-04 凭据传递与日志脱敏。
- CR-P1-09 构造失败资源清理。
- CR-P1-05 无活动数据库明确失败。
- CR-P1-07 先完成并发排空输出和 stdin EOF，deadline 另行灰度。

### 阶段 2：事务与锁

1. 先设计并实现 CR-P0-02 的单次释放与 owner drain 分离。
2. 再实现 CR-P0-01 的事务长持锁和终止状态机。
3. 全实例统一升级并执行事务/激活故障测试。

### 阶段 3：同步正确性

- CR-P1-02 先取消危险优化，恢复正确性。
- CR-P1-03 增加 quarantine、约束恢复和人工恢复流程。
- 共同设计 CR-P1-01 文件协议与 CR-P0-03 H2 严格恢复。

### 阶段 4：分布式、执行器和健康状态机

- 先完成 CR-P1-10 私有时间语义。
- 设计 CR-P1-11 状态事件/generation。
- 在状态机稳定后灰度 CR-P2-02 observer enforce。
- 设计 CR-P1-06 requestId/结果分类，再处理 CR-P1-08 deadline/有界执行器。
- 明确 CR-P2-01 的多集群线程池所有权。

### 阶段 5：产品和平台决策

- 对 CR-P1-12 选择 fail fast、实现或主版本删除。
- 对 CR-P2-03 明确构建 JDK 与运行 JDK 支持矩阵，分阶段升级 Wrapper/JAXB/插件。

## 14. 开放问题

- 生产是否实际使用手工事务、H2 dump/restore、`versionPattern` 和 `pool/sql`？调用量决定灰度和兼容窗口，但不改变正确性结论。
- 当前成员离开时是否允许强制释放该成员全部锁？若允许，owner 身份和 generation 如何定义？
- H2 本地目标的部署形态是独立文件、嵌入式进程还是同 JVM 多库？这决定安全恢复方式。
- 可选 observer 的真实业务语义是 OR、加权投票还是仅诊断？
- 对 JDBC 写超时的 unknown outcome，现有 durability 是否足以持久化和恢复？
- JDK 17 的目标是“构建兼容”还是“运行时正式支持”？

## 15. 评审结论

- 可以优先实施：CR-P0-04、CR-P1-05、CR-P1-09、CR-P2-04，以及 CR-P1-07 的输出排空/EOF 子项。
- 必须先做专项设计：CR-P0-01、CR-P0-02、CR-P0-03、CR-P1-01、CR-P1-03、CR-P1-04、CR-P1-06、CR-P1-08、CR-P1-11、CR-P1-12、CR-P2-01、CR-P2-03。
- 可以先做兼容性降级：CR-P1-02 取消 `versionPattern` 优化；CR-P2-02 先 shadow；CR-P1-10 先只移除全局时钟副作用并保持接口语义。
- 高风险项的验收标准必须是故障场景下保持正确状态，而不只是现有 515 项测试继续通过。
